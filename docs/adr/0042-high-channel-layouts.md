# 0042. 채널은 64개까지 받고, 고채널 배치는 자리 표를 넓혀 적는다

상태: 채택, 2026-10-28. ADR 0029의 자리 표와 기본 직접 배치, ADR 0024의 PCM 형식 규칙, ADR 0025의 ASIO 배치, ADR 0034의 앱 배치를 넓힙니다.

## 배경

Impulcifer 3.x는 13.1, 22.2, 24.1.10, 30.2 배치를 측정합니다. 배치마다 파일 하나(아래 '배치 파일')를 쓰고, `hrir.wav`는 82트랙, `hesuvi.wav`는 80트랙까지 씁니다. Spatial SoftReceiver는 이 가운데 어느 것도 받지 못했습니다.

- 채널 수의 상한이 32입니다. 드라이버 계약의 직접 출력 집합이 u32 비트라 33채널 이상을 나타내지 못하고, 디코더, 엔진, 출력, 스피커 프로필, ASIO가 모두 32에서 멈춥니다. 24.1.10은 35채널입니다.
- 자리 표(ADR 0029)에 귀 아래 자리, 위층의 낮은 고리, 135°·120°·165°·75°·10° 자리가 없습니다. 그래서 22.2, 30.2, 24.1.10은 자리를 겹치지 않고는 적을 수 없었습니다(ADR 0029의 24채널 한계).
- 한 배치에 LFE를 하나만 둡니다. 22.2와 30.2에는 LFE가 둘입니다.
- 9.1.x가 두 가지로 적혀 있습니다. 프리셋과 직접 배치 기본값은 ffmpeg를 따라 7·8번 채널이 ±15°의 `Lc/Rc`이고, ASIO의 9.1.6은 ±60°의 와이드 `Lw/Rw`입니다. Dolby의 9.1.x와 Impulcifer가 측정하는 9.1.6(`hrir.wav` 32트랙)은 와이드를 씁니다. 그래서 와이드로 믹스한 소스가 마스크 0으로 오면 와이드가 ±15°에서 들렸습니다.
- BRIR은 `hrir.wav` 32트랙, `hesuvi.wav` 30트랙까지만 읽고, 배치 파일은 읽지 못합니다.

## 결정

### 채널 상한은 64

- PCM, 엔진 출력, 스피커 프로필의 장치 채널, 업믹스, ASIO의 채널 상한을 64로 올립니다. 이미 64인 방향 수(`Layout::MAX_DIRECTIONS`), 객체 수(`MAX_OBJECTS`)와 같은 값입니다. 채널을 한 비트씩 담는 집합은 u64입니다.
- 드라이버 계약(`ssr-abi`)
  - `MAX_PCM_CHANNELS`는 64입니다.
  - `PcmFormats`의 직접 출력 집합은 64비트이고, 비트 c-1이 c채널입니다. 구조체에 암묵적인 채움 바이트를 두지 않습니다.
  - 마스크가 있는 PCM의 상한은 그대로 18입니다. Windows 스피커 비트가 18개이기 때문입니다.
  - `DIRECT_DEFAULT_CHANNELS`에 24, 32, 35를 더합니다(아래 '기본 직접 배치').
  - 볼륨 기록은 그대로 32채널입니다. 엔진은 기록의 채널 이득을 한 값으로 줄여 엔드포인트 전체에 걸기 때문에(ADR 0024) 스트림의 채널 수와 상관이 없습니다.
  - 계약은 아직 동결 전이므로(ADR 0027의 2026-10-17 고침) 판을 올리지 않고 고치고, C 헤더와 Python 모듈을 다시 생성합니다.
- 드라이버: 레지스트리의 `PcmDirectChannels{n}`(DWORD)은 지금처럼 1~32채널을 맡고, 33~64채널은 새 값 `PcmDirectChannelsHigh{n}`(DWORD, 비트 c-33이 c채널)이 맡습니다. INF의 기본값은 둘 다 `0xffffffff`이고, 값이 없으면 컴파일된 집합을 씁니다. KS 데이터 범위의 최대 채널 수는 지금처럼 마스크 상한과 켠 직접 채널 수 가운데 큰 값입니다.
- Windows 오디오 엔진이 공유 모드에서 33채널 이상의 스트림을 받는지는 아직 확인하지 않았습니다. 확인하는 절차는 시험서명 PC 문서에 둡니다. ASIO 입구는 Windows 오디오 엔진을 거치지 않으므로 이 확인과 상관없이 64채널까지 받습니다.

### 자리 표에 17자리를 더한다

ADR 0029대로 공칭 자리는 `Speaker` 표 하나에 있고, 물리적으로 다른 자리에는 다른 이름을 붙입니다. 이번 배치들이 쓰는 자리 가운데 표에 가까운 자리가 있으면 그 자리를 쓰고, 한 배치 안에서 두 채널이 같은 자리로 모이거나 가까운 자리가 없을 때만 새 이름을 만듭니다.

| 이름 | 방위 / 고도 | 쓰는 배치 |
| --- | --- | --- |
| `Lsc`, `Rsc` | ±10° / 0° | 24.1.10 |
| `Ls1`, `Rs1` | ±75° / 0° | 24.1.10 |
| `Lrs1`, `Rrs1` | ±120° / 0° | 24.1.10 |
| `Lbs`, `Rbs` | ±135° / 0° | 22.2, 24.1.10 |
| `Lcs`, `Rcs` | ±165° / 0° | 24.1.10 |
| `Hfl`, `Hfr` | ±30° / 30° | 30.2, 24.1.10 |
| `Hrl`, `Hrr` | ±150° / 30° | 30.2, 24.1.10 |
| `Bfl`, `Bfr` | ±45° / −30° | 22.2, 30.2 |
| `Bfc` | 0° / −30° | 22.2, 30.2 |

- `Lbs/Rbs`(135°)와 `Lrs/Rrs`(150°)는 다른 자리입니다. ffmpeg 이름 `BL/BR`은 지금처럼 `Lrs/Rrs`입니다.
- `H`로 시작하는 자리는 `T`로 시작하는 위층(고도 45°)보다 낮은 고리입니다. 30.2와 24.1.10은 위층에 높이가 다른 고리를 둘 두므로 따로 이름을 붙였습니다. 고도 30°는 ITU-R BS.2051의 위층 공칭값입니다.
- `B`로 시작하는 귀 아래 자리의 고도는 −30°입니다. ffmpeg 이름 `BFC`, `BFL`, `BFR`은 `Bfc`, `Bfl`, `Bfr`입니다.
- 표에는 위치가 있는 자리 40개와 LFE 둘이 있습니다. ADR 0029의 24채널 한계는 없어집니다.

### 배치

배치는 채널 순서대로 자리를 적은 것이고(`ssr_types::channel_layout_preset`), 이름은 숫자로만 씁니다.

| 배치 | 채널 | 자리(채널 순서) |
| --- | --- | --- |
| 9.1 | 10 | L R C LFE Lrs Rrs Lss Rss Lw Rw |
| 9.1.4 | 14 | 9.1 뒤에 Tfl Tfr Trl Trr |
| 9.1.6 | 16 | 9.1 뒤에 Tfl Tfr Tsl Tsr Trl Trr |
| 13.1 | 14 | L R C LFE Lrs Rrs Lss Rss Tc Tfl Tfc Tfr Trl Trr |
| 22.2 | 24 | Lw Rw C LFE Lbs Rbs L R Cs LFE2 Lss Rss Tfl Tfr Tfc Tc Trl Trr Tsl Tsr Trc Bfc Bfl Bfr |
| 24.1.10 | 35 | L R C LFE Lss Rss Lbs Rbs Lw Rw Tfl Tfr Tsl Tsr Trl Trr Lc Rc Lsc Rsc Ls1 Rs1 Ls Rs Lrs1 Rrs1 Lrs Rrs Lcs Rcs Cs Hfl Hfr Hrl Hrr |
| 30.2 | 32 | C L R Ls Rs LFE Cs Lrs Rrs Lss Rss Lc Rc Hfl Tfc Hfr LFE2 Lw Rw Tc Tsl Tsr Trc Hrl Hrr Bfc Bfl Bfr Tfl Tfr Trl Trr |

- **9.1.x는 와이드를 씁니다.** 7.1의 순서(Windows 마스크 순서라 뒤쪽 쌍이 옆쪽 쌍보다 먼저입니다) 뒤에 `Lw/Rw`를 두고, 위층은 앞, 옆, 뒤 순입니다. ASIO의 9.1.6, Impulcifer `hrir.wav` 32트랙과 같은 순서입니다. 그래서 지금의 9.1.4와 9.1.6 프리셋, 14·16채널 직접 배치 기본값이 바뀝니다. ffmpeg의 9.1.x(`Lc/Rc`)로 보내는 소스는 `--direct-layout`에 자리 이름으로 적습니다. Windows 스피커 비트에는 와이드가 없으므로 9.1.x는 마스크로 나타내지 못합니다.
- **13.1**은 Windows 마스크 `0x2FE3F`의 비트 순서와 같습니다. 이 배치의 소스는 마스크를 달고 오고, 마스크는 지금처럼 비트마다 표의 자리가 됩니다. 그래서 13.1의 위층은 이 배치 본래의 고도 30°가 아닌 7.1.4와 같은 45°이고, 옆 쌍(110°)은 `Lss/Rss`(90°)입니다. 같은 배치의 BRIR 파일도 이 자리로 읽으므로(아래 'BRIR') 13.1 소스는 채널마다 제 BRIR 방향에 놓입니다.
- **22.2**는 SMPTE ST 2036-2의 순서입니다. 위층 고리(규격 고도 30°)는 표의 45° 고리에 놓습니다. 22.2는 위층 고리가 하나뿐이어서 겹칠 자리가 없고, 그래야 7.1.4로 측정한 BRIR에서도 22.2의 위층 채널이 위층 방향에 그대로 놓이기 때문입니다.
- **30.2**는 ETSI TS 103 491 표 B-5의 마스크 순서입니다. 규격이 이 배치의 PCM 채널 순서를 정하지 않으므로 Impulcifer의 배치 파일과 같은 순서를 씁니다.
- **24.1.10**은 공개된 채널 순서가 없으므로 Impulcifer의 배치 파일과 같은 순서를 씁니다. 1~16번은 Dolby와 Apple 등이 쓰는 9.1.6 교환 순서이고, 17~35번은 설치 안내서의 나열 순서입니다. 그래서 1~16번은 위 9.1.6과 순서가 다릅니다(옆쪽 쌍이 뒤쪽 쌍보다 먼저입니다).

### 기본 직접 배치

ADR 0029의 기본 직접 배치 표를 다음처럼 고칩니다.

| 채널 수 | 배치 |
| --- | --- |
| 1~6, 8, 10, 12 | 지금과 같습니다(10은 7.1.2, 12는 7.1.4) |
| 14 | 9.1.4(와이드로 바뀝니다) |
| 16 | 9.1.6(와이드로 바뀝니다) |
| 24 | 22.2 |
| 32 | 30.2 |
| 35 | 24.1.10 |

- 10채널의 9.1과 14채널의 13.1은 같은 채널 수에 다른 기본값이 있으므로 `--direct-layout`으로 고릅니다. 13.1 소스는 대개 마스크를 달고 옵니다.
- 프리셋 이름(`decode::direct::preset`)에 `9.1`, `13.1`, `22.2`, `24.1.10`, `30.2`를 더합니다.

### LFE 둘

- 한 배치에 `LFE`와 `LFE2`를 하나씩 둘 수 있습니다. 같은 LFE를 두 번 둔 배치는 지금처럼 시작하기 전에 거절합니다.
- 장면의 LFE는 하나이므로 디코더는 두 채널을 더해 장면의 LFE에 넣습니다. 이득은 각각 1입니다. 22.2와 30.2는 서브우퍼 둘이 함께 울리는 방에서 믹스하므로, 두 채널을 더한 것이 그 방에서 들은 저음이기 때문입니다.
- 마스크가 있는 PCM에는 LFE 비트가 하나뿐이라 LFE가 둘인 경우가 없습니다.

### 앱의 스피커 배치 (ADR 0034)

- `SpeakerLayout`에 9.1, 9.1.4, 9.1.6, 13.1, 22.2, 24.1.10, 30.2를 더합니다. 순서와 자리는 위 '배치'와 같습니다.
- Windows 마스크가 있는 배치는 그 마스크로 엽니다(13.1은 `0x2FE3F`). 마스크가 없는 배치(9.1.x, 22.2, 24.1.10, 30.2)는 마스크 0의 직접 출력으로 엽니다. 장치는 채널을 순서대로 내보냅니다. 모든 앱 배치에 Windows 마스크가 있다던 ADR 0034의 문장은 이 고침으로 바뀝니다.
- 장치가 그 배치를 여는지 미리 묻는 검사(`supports_layout`)는 새 배치도 그 형식 그대로 묻습니다.
- 스피커 프로필에 서브우퍼가 둘이면 둘 다 장면의 LFE를 받습니다.

### ASIO (ADR 0025)

- ASIO 배치에 9.1, 9.1.4, 13.1, 22.2, 24.1.10, 30.2를 더합니다. 채널 순서는 위 '배치'와 같습니다. 기존 다섯 배치의 선 값(0~4)과 채널 이름은 그대로 두고, 새 배치는 그 뒤에 값을 이어 붙입니다.
- 켠 채널의 집합은 64비트입니다.

### BRIR

- **3.x의 `hrir.wav`와 `hesuvi.wav`.** Impulcifer 3.x는 2.x 순서 뒤에 새 자리 25개를 자기 자리 표의 순서로 붙이고, 측정하지 않은 뒤쪽 자리는 잘라냅니다. 그래서 `hrir.wav`는 82트랙, `hesuvi.wav`는 80트랙까지 읽습니다. `LFE2`는 이 파일들에 없습니다.
  - 새 자리의 이름은 Impulcifer의 자리 이름(FCL, SCL, SL1 등)이고, 각도는 Impulcifer 3.x의 공칭값입니다.
  - 2.x 순서보다 트랙이 많은 파일은 3.x가 쓴 것이므로 모든 자리의 각도를 3.x의 표로 정합니다(BL 135°, HBL 135°/30°, TSL 90°/65° 등). 3.x가 2.x 자리만 측정한 파일은 2.x 파일과 바이트까지 같아 구별할 수 없으므로 지금처럼 프로필의 각도 프리셋을 씁니다. 어느 쪽이든 각도 덮어쓰기가 마지막에 적용됩니다.
  - 측정한 BRIR의 각도를 자리 표와 묶지 않는다는 ADR 0029의 원칙은 이 파일들에 그대로 적용됩니다.
- **배치 파일.** Impulcifer 3.x의 배치 파일은 배치의 채널마다 왼쪽 귀와 오른쪽 귀 두 트랙을 두고, LFE 자리는 무음 두 트랙으로 채웁니다. 파일에는 `ICHL` 청크(`{"version":1,"tracks":[...]}`)가 있어 트랙마다 그 배치의 채널 이름표와 귀가 적혀 있습니다.
  - `ICHL`의 이름표가 지원하는 배치 하나의 채널 이름표와 순서까지 같으면 그 파일을 그 배치의 BRIR로 읽습니다. 파일 이름은 보지 않습니다. 이름표 표는 `brir`에 둡니다.
  - LFE가 아닌 채널이 방향 하나가 되고, 방향의 각도는 그 배치의 같은 번째 자리(위 '배치')의 공칭 각도입니다. 측정한 위치가 아닌 배치의 공칭값을 쓰는 이유는, 그래야 같은 배치의 소스가 채널마다 정확히 제 방향에 놓여(VBAP 이득 1) 다른 방향과 섞이지 않기 때문입니다. 다른 배치의 소스는 이 방향들 사이에 VBAP로 놓입니다.
  - 측정한 BRIR의 각도를 자리 표와 묶지 않는다는 ADR 0029의 원칙에서, 배치 파일은 예외입니다. 배치 파일의 채널은 곧 그 배치의 자리이기 때문입니다.
  - LFE 트랙은 읽지 않습니다. 이름표가 맞지 않거나 `ICHL`이 없는 다채널 파일은 지금처럼 CSV 곁파일이 있어야 읽습니다.
- 앱의 BRIR 가져오기는 폴더, `hesuvi.wav`, `hrir.wav`에 더해, 지원하는 배치의 `ICHL`이 있는 WAV도 받습니다.

### 이름

배치 이름은 숫자로만 씁니다. 형식과 제품의 이름(Auro-3D, NHK, Dolby Atmos, DTS:X Pro)은 코드의 식별자, 파일 이름, 화면 문구에 쓰지 않습니다. README에 호환되는 형식을 사실로만 적고 상표 고지를 둡니다.

### 화면

- 세 스킨의 스피커 배치와 ASIO 배치 고르기에 새 배치가 모두 나옵니다.
- 세 스킨의 방향 지도는 귀 아래 방향을 귀 높이, 위층과 다른 모양으로 그리고 범례에 적습니다.

## 결과

- Impulcifer 3.x의 배치 파일을 가져오면 같은 배치의 소스가 채널마다 제 방향으로 렌더됩니다.
- 와이드로 믹스한 9.1.x가 ±60°에서 들립니다. ffmpeg 순서의 9.1.x를 마스크 0으로 보내던 소스는 자리 이름으로 배치를 적어야 합니다.
- 24.1.10은 ASIO로 받습니다. Windows 엔드포인트로 33채널 이상을 받는 일은 시험서명 PC에서 확인하기 전까지 보장하지 않습니다.
- 22.2와 30.2의 두 LFE는 합쳐서 들립니다. 스피커 출력에서 서브우퍼 둘을 따로 먹이지는 않습니다.
- 13.1의 위층은 이 배치 본래의 30°가 아닌 45°로 렌더됩니다. 13.1을 다른 배치의 BRIR로 들을 때만 차이가 납니다.

## 2026-10-29 고침 (교차 링의 크기)

v0.26.0은 교차 링을 엔진 출력의 상한에 맞춰 64채널 분량으로 만들었습니다. 그 뒤 CI의 windows-2025 러너에서 live audio 잡이 네 번 가운데 세 번 실패했습니다. 독점 소크에서 장치가 원본보다 8% 남짓 느리게 소리를 가져가고, ASRC가 +2000 ppm 상한에 붙고, 지연이 수 초까지 늘었습니다. 같은 시간대의 v0.25.1은 통과했습니다. 렌더 결과는 두 판이 바이트까지 같았고, 교차 링만 32채널 분량으로 되돌린 판은 v0.25.1과 같은 모양(시계 0 ppm, 지연 62 ms)으로 통과했습니다. 링이 커진 것이 어떤 경로로 이 차이를 낳는지는 찾지 못했습니다.

그래서 교차 링은 다시 `capacity_ms`의 32채널 분량을 담습니다(`CROSSING_RING_CHANNELS`). 32채널까지의 출력은 지금처럼 `capacity_ms` 전부를 담고, 그보다 넓은 출력은 `capacity_ms × 32 / 채널 수`를 담습니다(64채널이면 기본 320 ms의 절반인 160 ms). 출력 쪽 제어기는 이 실제 용량을 씁니다.
